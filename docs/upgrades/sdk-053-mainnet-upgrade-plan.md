文档日期：2026-09-10；进度更新：2026-09-12  
状态：执行方案，尚未满足主网升级放行条件  
本阶段唯一目标：安全完成 0.4.4 → SDK 0.53 桥接版本升级，并保持原有链上业务正常。

## 2026-09-12：桥接分支提交整理

本次将此前本地的兼容修复、已批准治理参数、回归测试和审查材料纳入桥接分支，供 GitHub 审查及候选 CI 验证。相对 `0.4.4` 清理无功能意义的格式、引用调序和函数搬移；四个历史升级常量文件恢复为与原版本逐字节一致。VS Code 显示与保存设置仅保留在本地，不纳入提交。

下文及审计附件中“尚未提交”的描述记录的是各次审查当时的状态。新增文本附件仅规范化行尾与尾部空格，配置字段和值未变。JSON 源码哈希和旧测试日志同样保留其采集时点，不作为本次最终提交或发布包的哈希。当前提交仍需通过 GitHub CI、重新构建 Linux 候选包，并按 `0.5.0` 计划名重跑受影响的升级验收；本次不创建正式 Release 或主网升级高度。

## 2026-09-12：纠正对 0.4.4 原代码的无依据删除

- 恢复 `0.4.4` 历史升级 handler、import 和 store-loader 分支；函数体与旧版一致，仅适配 context。
- 恢复 SDK 仍支持的 legacy params 治理路由及 CLI；恢复旧 Ante 装配/错误、原始 Wasm capability 列表及无关删改。
- 恢复 Docker Ledger 编译选项、linux-headers 和旧 `GIT_COMMIT` 构建参数；Linux 最终镜像仍需验证。
- 必须保留的版本适配和不可直接恢复的已移除上游接口，逐项列于 [原代码保留复核](../security/sdk-053-baseline-preservation-2026-09-12.md)。升级前还需清点待执行的 legacy software-upgrade / IBC proposal，不能把旧序列化类型仍存在当作旧执行 handler 仍可用。
- 本轮未提交、发布或替换远程演练节点。最终包重新演练的要求不变。

## 2026-09-12：按版本要求收敛桥接范围与治理政策（晚于上述 RC1）

用户要求区分升级必需项、已验证的兼容修复及无业务依据的额外功能。逐项依据和提交来源见 [必要性审查](../security/sdk-053-necessity-review-2026-09-12.md) 与 [逐文件来源清单](../security/sdk-053-change-provenance-2026-09-12.csv)。这次变更仅在本地工作区，未替换正在运行的演练网或发布新包。

- 移除自定义 proposal 处理器、100M gas/bytes 兜底与参数重写，使用 SDK 0.53.6 默认接线；保留真实旧共识记录的迁移和校验。

**新增 Go/No-Go 项：** 从 0.4.4 升级前副本按 `0.5.0` 重新演练；核对新 IBC 接线的往返/超时/在途包、首块和重启 gas 参数及治理参数表；重新构建 Linux 候选并固定身份。旧 RC1 的 commit/产物/旧接线验收记录不得覆盖或借用作新版本验收。真实 Wasm 业务和持续稳定性门槛保持待验收。

## 1. 先明确我们要完成什么

这次只做基础版本升级，不叠加 PQC 账户、PQC 签名、验证人密钥轮换或新的产品功能。后续 PQC 工作单独规划。

升级成功必须同时满足：链恢复出块、各节点对状态达成一致、用户资产与业务状态正确、原有合约和跨链业务可用、节点可重启和恢复。只看到新区块，不算验收完成。

这不是验证人手工搬运数据库的工作。复杂处理应封装在经过验证的程序中；验证人最终执行的是备份、预置发布包、按约定高度切换和验收。

## 3. 第一步：收集基线并冻结升级范围

### 准备材料

- 实际节点版本、操作系统/CPU 架构、数据库后端、磁盘剩余空间、内存、pruning/snapshot 配置。
- 验证人名单与投票权、联系人、运行方式（Cosmovisor 或 systemd）、远程签名器配置。
- 主网模块版本表、共识参数、余额和业务状态清单。
- 现有合约地址/code ID/校验值、关键调用方式、relayer 和钱包/indexer 依赖的接口。
- 每项验收的负责人，以及问题记录和升级期间协调渠道。

### 准备方式

运维从实际节点收集配置和版本；公开 RPC 用于只读查询及记录高度，不能替代服务器备份。私钥不进入普通文档、仓库或共享日志。生成带高度、时间及校验值的基线文件。

以下是 2026-09-10 高度 17,236,364 的已知事实，属于历史检查点，不是升级当天的保证：

| 项目 | 已知结果 | 后续处理 |
|---|---|---|
| feeibc store | 已验证为空 | 临近升级重查，模块余额也需单独检查 |

| transfer | 17 个通道，其中 14 OPEN | 覆盖旧通道跨链业务 |
| Wasm channel-16 | OPEN，ics721-1 | 保留状态与资产检查；完整 NFT 跨链流程按范围调整暂缓 |

### 验收

范围内只包含 0.53 基础升级；每个重要业务都有测试对象和负责人。无法取得主网快照或没有业务验收对象，不进入正式上线阶段。

## 4. 第二步：修复代码，补齐升级保护和测试

### 准备材料

现有审计报告、0.4.4 源码、桥接源码、固定依赖版本、错误复现测试和链上基线。

### 实施方案

| 工作项 | 如何处理 | 如何证明完成 |
|---|---|---|
| 空 IAVL 树兼容 | 消除对可缺失/替换的本地计划文件的脆弱依赖，保留损坏状态拒绝加载保护 | 旧空根、实际升级后提交、重启、换计划文件和快照恢复测试 |
| ICA 接线 | 移除重复 controller 层，按真实鉴权模型接线 | 旧状态的注册、握手、ack、timeout 和回调测试 |
| 源状态检查 | 明确允许的模块版本表及共识参数来源；异常状态给出明确错误 | 正常源状态通过、错误/缺失/损坏输入被明确拒绝 |
| feeibc 移除条件 | 新增可重复的升级前检查；若需程序内保护，应在旧 store 被移除之前读取并验证 | 非空样本不能被无声删除；空样本正常升级 |
| capability 移除 | 保留上游移除方向，验证 transfer/ICA/wasm 路由和权限 | 原通道可继续操作，错误端口/合约操作被拒绝 |
| 共识预算 | 确认有限 gas/字节预算和费用政策；不让默认变更未经评估进入生产 | 大交易、连续序列号、非法签名、gas 边界和不同节点配置测试 |
| 模拟设施 | 隔离每个实例的 Wasm 缓存，正确关闭资源 | 显式启用的确定性、导入导出和模拟套件完成 |

特别说明：当前 StoreLoader 会先删除旧 store。不能简单在删除之后的 handler 里读取 feeibc 再决定是否退款。发现非空时，应暂停放行并设计保留/结算顺序，而不是让操作员手工清数据。

### 验收

普通测试与显式模拟均通过；已知高风险项有回归证据；代码经第二人复核。此时只能称“可演练候选”，仍不能直接称“主网可用”。

### 准备材料

目标节点架构、固定候选 commit、Go 工具链、匹配 WasmVM 3.0.7 的原生库、CI 构建环境及发布位置。

- 固定构建依赖和下载校验，下载/链接失败必须让流程失败。
- 为实际使用的 Linux 架构构建产物；AMD64/ARM64 若均部署，均需验证。
- 输出 release tag、commit、工具链、原生库版本、二进制 SHA-256 与构建日志。
- 用这些实际二进制进行启动、合约执行和重启冒烟测试，不用开发机另编译的程序替代。
- 核对应用的版本报告与发布记录，验证人可以确认正在运行哪一个产物。

正式交付形式的二进制通过测试；所有后续演练使用这些产物。同架构节点核对同一哈希；不同架构产物允许不同哈希，但必须通过同输入状态一致性验证。

## 6. 第四步：准备真实快照和隔离演练环境

### 准备材料

- 来自实际 0.4.4 节点的完整、一致快照。
- 应用数据库、CometBFT 数据、Wasm 文件、配置和升级元数据的备份清单。
- 足够容纳旧数据、备份、迁移写入和测试产物的磁盘空间；依据实际大小测量，不假定固定倍数一定足够。
- 建议至少 4 个隔离测试验证人节点，另有查询/恢复节点；明确测试投票权分布。
- 必要的 IBC 对端测试环境或可验证的双链测试装置。

### 实施方案

1. 对专用节点采用停机一致备份，或经过验证的文件系统一致快照方案；不要把运行中的数据库随意复制后视为可恢复备份。
2. 标注高度、AppHash、文件范围和 SHA-256。保留一份独立副本。
3. 实际用 0.4.4 恢复，确认读取和基线导出成功；“文件已上传”不等于恢复测试通过。
4. 建立完全隔离的测试网络，阻断主网 peer 和主网 relayer。主网签名私钥不得进入演练环境。
5. 从主网快照建立可出块的隔离分叉需要专门工具与方法：记录测试 chain ID、验证人集合及必要 consensus/signing 元数据的变更，使用测试密钥。仅换一套密钥无法使原主网验证人集合继续出块。
6. 将上述测试专用变化列入允许差异，不重建或清空待验证的应用业务状态。先验证隔离分叉能用旧版运行，再从其基线做迁移。

### 验收

旧版恢复成功；测试专用变更可解释、可重复；基线业务状态得到保留；网络和密钥隔离已经核验。正式主网原地升级仍需按步骤 8 执行，分叉演练不是直接替换主网数据库的方法。

## 7. 第五步：完整升级与业务回归

### 准备材料

步骤 3 的二进制、步骤 4 的环境与基线、业务测试账户、合约调用样本、跨链测试装置和状态核对程序。

### 实施方案

在隔离环境走实际软件升级流程，计划名使用 `0.5.0`：旧版到测试升级高度停止 → 新版加载并迁移 → 提交升级块 → 连续出块。不要用新 genesis 启动成功替代原地迁移测试。

逐项核验：

| 对象 | 必查内容 |
|---|---|
| 共识 | 升级高度及后续节点同高度 AppHash 一致、区块继续提交 |
| 账户/银行 | 余额、总供应、模块余额；解释奖励/手续费等正常变化 |
| staking/distribution | 委托、解委托、验证人权重、奖励与模块池不变量 |
| 授权/治理 | authz、feegrant、现有提案和参数能读取与执行 |
| Wasm | code checksum、合约状态、pinned code、代表性 execute/query |
| IBC | clients、connections、18 个 channels、packet/ack/序列和托管余额 |
| ICS-721 历史状态 | channel-16、原合约、NFT 归属及历史 packet 不丢失；完整业务流程暂缓，不标记为通过 |
| capability | 旧 store 按预期移除，业务身份和权限检查仍正常 |
| feeibc | 迁移前零状态条件满足，不引入未解释余额 |
| 提案和接口 | 非法/边界交易、不同 min-gas-prices、钱包、RPC、indexer、relayer |

跨链验证需要有效对端与证明。隔离分叉不能直接用主网对端继续完成跨链测试；需准备兼容对端分叉或测试夹具，说明覆盖到哪些真实状态。若 channel-16 的实际合约路径没有被覆盖，不把普通转账测试算作其通过。

升级前后 AppHash 不必相同，因为合法迁移会改变状态格式。要求的是：同高度新节点结果一致，业务不变量保持，所有允许差异有解释。

建议最低演练观察门槛为升级后至少 1,000 块且持续 24 小时，两项均满足；这是本方案建议的门槛，不是当前已完成结果。另对超时、解委托等较长周期使用专门测试场景，不能认为 24 小时覆盖全部生命周期。

### 验收

全部必查项有结果；无未解释状态差异；无分歧、异常迁移或关键业务故障。记录迁移耗时、CPU/内存/磁盘峰值和可接受停机窗口。未通过则返回修复，不进入主网协调。

## 8. 第六步：重启与故障恢复演练

### 准备材料

已迁移环境、迁移前完整备份、迁移后快照、每个节点签名状态记录、恢复操作草案。

### 实施方案

只在隔离环境测试：

- 正常停止再启动至少两次。
- 缺失/替换升级计划文件后的兼容行为。
- 单节点离线再加入；保证剩余在线投票权大于 2/3 的场景下仍可出块。
- 迁移过程中异常退出后的重试/恢复。
- 使用迁移后快照恢复一个新节点。
- 正式操作员按文档执行恢复，记录时间和所需材料。

将恢复分成三类，分别写步骤：

| 场景 | 恢复原则 |
|---|---|
| 本地启动/迁移失败 | 保留日志和数据库，先确认提交边界及磁盘变化，再执行经过演练的恢复 |
| 网络已升级，单节点失败 | 使用正确的新版本修复或从兼容快照恢复追块 |
| 网络整体不能推进 | 验证人协调处置，禁止单节点自行回退网络；按已演练方案决定修复前进或协调恢复 |

新状态提交后不能直接用 0.4.4 打开同一数据库继续运行。即使迁移报错，也不能假定磁盘完全未变。不能回退签名记录、让两台机器共用主网密钥同时签名，或用 unsafe reset 掩盖问题。

### 验收

恢复手册被实际执行过，知道每种失败的处理边界；能够说明备份恢复耗时。涉及已签高度或全网历史的恢复必须协调，不能把“恢复旧备份”写成通用一键回滚。

## 9. 第七步：固定发布与验证人协调

### 准备材料

- 最终 commit/tag、二进制及哈希、迁移说明、演练结果和已知限制。
- 验证人操作手册：备份、预下载、校验、目录、配置、切换、检查、故障联系人。
- 各验证人投票权与就绪确认表，以及钱包/RPC/relayer/indexer 就绪表。
- 主网软件升级提案内容、治理流程和候选高度计算依据。

### 实施方案

先完成最终放行复核，再根据实际出块速度、治理投票期和协调缓冲确定高度 H，不按粗略时间直接指定。提案名与程序 handler 必须一致。

Cosmovisor 方式预先放置已验证二进制于`cosmovisor/upgrades/0.5.0/bin/dorad` 路径；不用未经核验的在线下载代替预置。使用 systemd 的节点也应有预演过的切换步骤。节点自己的 home、权限和签名器位置需按实际环境填写。

所有验证人均应协调，至少确保已确认升级就绪的投票权**严格大于 2/3**，并留出故障余量；不能只统计节点个数，也不能把“刚超过 2/3”当成理想目标。

临近 H 再检查 feeibc store、模块余额、版本和参数。若要依赖零状态作为删除前提，必须有明确的最后检查和程序保护策略；仅提前一天查询或通知 relayer 暂停不能保证期间没有新的费用状态。

### Go / No-Go 清单

- [ ] 已知高风险问题关闭，最终候选经复核。
- [ ] 最终发布包完成真实快照升级、业务与恢复演练。
- [ ] 状态差异全部可解释；Cosmos Hub/Osmosis/Noble 资产业务验收通过；包括 ICS-721 在内的历史资产状态保留，未测试范围明确记录。
- [ ] 备份确实恢复过，恢复手册完整。
- [ ] feeibc 零状态前提再次核实并有边界处理。
- [ ] 验证人按投票权达到就绪目标且有余量。
- [ ] 高度、计划名、产物和操作文档一致。
- [ ] 维护窗口、监控、响应人员及异常处理方式明确。

任何关键项未完成，不安排执行。若治理提案已经通过而发现阻断项，必须按链支持的治理/协调机制处理计划，不能假设本地口头推迟即可取消链上升级。

## 10. 第八步：正式升级与验收

### 升级前

核实计划高度 H、产物哈希、备份和签名器状态。记录接近升级高度的基线，按演练方案减少高风险业务活动。准备最终一致备份/恢复点，具体耗时由演练确定。

### 到达 H

旧程序按计划停止；执行已演练的切换方式；新程序自动加载并迁移。观察迁移日志、提交高度、AppHash、在线投票权和节点资源。不要手工删 capability，不跳过迁移，不在异常时反复切换新旧程序试运气。

超出演练确定的耗时窗口、节点结果分歧或关键迁移错误，立即进入协调处置，保留证据并暂停业务放量。

### 恢复出块后

先做只读状态核对，再执行经批准的小额业务验证。检查关键接口、合约、跨链与 relayer；按验收结果逐步恢复业务。观察至少 24 小时，并对尚未触发的长周期业务继续跟踪。该观察安排需实际落实给人员，不代表本文已经创建监控任务。

### 完成标准

所有必要验证人与服务恢复正常；多节点同高度状态一致；资产与业务验收完成；无未解释故障。保留备份、发布包、参数、演练/上线日志和恢复方案，记录最终版本及完成高度。到这里才宣布 0.53 升级阶段完成。
