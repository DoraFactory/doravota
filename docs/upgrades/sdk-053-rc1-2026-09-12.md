## 本轮完成的底层检查

### 有效期内重复包

在受控对端与快照升级链之间分别完成正、反向测试。关闭高度超时并设置一小时 timestamp timeout；更新客户端后，用与已验证共识高度匹配的真实 ICS-23 commitment proof 构造收包交易。第一次收包执行成功，随后用接收方账户的新 sequence 对同一个 MsgRecvPacket 重新签名。

两次重放均在包有效期内被 CheckTx 拒绝：`codespace=channel, code=22, packet messages are redundant`。不是过期、账户 sequence 或签名错误。没有重复到账。反向测试接收方是原主网快照升级后的 Vota 链。最终所有测试跨链本金已转回，双方 packet commitments 清空，对端测试 voucher 余额归零；交易费单独消耗。

准备脚本曾发生容器入口/用户、证明高度、事件 `packet_data_hex` 解析错误；这些失败尝试留档，未计入通过，也未导致链代码修改。成功证据见 `duplicate-valid-complete/`、`duplicate-inbound/` 与 `duplicate-final-settlement.json`。

### 从空数据库进行 state-sync

新建独立非验证节点，不复制应用数据库、不复用任何验证人签名密钥。通过测试网节点发现并导入高度 `17269200` 的 format 3 快照（51 chunks）。追块后五个节点均到达 `17269719`；在 `17269717` 比较区块哈希和 AppHash，全部一致。

旧 `…rmgg4` registry 的 admin、next poll ID 和 aMACI code ID 查询与源节点一致。进一步按链上 156 个 code 记录核对 112 个不同 checksum，对应 Wasm 字节码全部恢复，内容与源节点相同。旧源目录额外保留 24 个无 `.wasm` 扩展名的旧格式副本；不能把目录文件数量直接当作链上 code 数量或丢失证据。

证据：`state-sync-start.json`、`state-sync-result.json`、`state-sync-milestones.log`、`state-sync-wasm-files.json`。

### 负载与日志

首轮 80 笔有效银行转账在三个块内成功，伴随 180 次余额查询无失败。该短突发仅持续约 6.7 秒，不作为吞吐上限或持续负载验收。后续持续负载 350.33 秒，600 笔有效转账全部成功，伴随 9,228 次余额查询无失败。查询 p95 约 2.83 ms（同机 loopback，不代表公网延迟）；出块间隔中位数 2.313 秒、最大 2.685 秒。70 次资源采样中，普通验证节点的 Docker 内存使用量采样峰值约 2.054 GiB，正在导出快照的 node3 上限 6.254 GiB，state-sync 节点上限 4.343 GiB。Docker CPU 百分比按单核计，node3 峰值 244% 约为 2.44 核。该有限负载不能证明最大容量、长时间泄漏或生产硬件配置足够。

测试 provider 的每 100 块快照间隔短于单次导出耗时，出现 `snapshot operation is in progress`。RC 运行时将间隔调为 1,000 块，保留最近两份；生产值仍需结合真实出块时间、快照耗时和磁盘预算确定。

四个验证节点连续 300 个同高度区块的 block hash/AppHash 一致。检查最近 30 分钟可取得的日志：有计划重启产生的连接关闭/重连、快照间隔过短导致上一快照未结束的 conflict，以及 9 次 RPC 查询暂时找不到 block results。9 个高度事后全部能成功查询；未发现这些高度的持久结果缺失，但这不证明所有历史日志均无错误。不能将以上有限窗口扩大描述成 24 小时稳定性验收。

本轮节点使用的底层演练二进制是 review5（SHA-256 `066360c4ff46696bb41162b7ce5a505e58325311a3b73fefef07a90f5057bfe1`）；RC 的应用行为修复与之相同，本轮新增的是版本元数据和发布流程修改。最终 RC 包的实际运行验证单独记录，不能混同哈希。四个验证节点与 state-sync 节点已依次换用 commit `c529f8d` 的 RC 静态包并重启，分别在高度 17270010/12/14/16/18 确认恢复；旧容器停止保留，原数据目录继续使用。

换包后再次执行双向有效期内重复包检查，均明确返回 channel/code 22，无重复到账；在高度 `17270051` 五节点 block hash/AppHash 一致，旧 registry 三项查询一致。随后五节点连续 100 个高度的 block hash/AppHash 一致；RC 日志中的匹配项为滚动重启时的连接中断、重连与 blocksync 超时，已恢复追块，没有观察到持久停块或哈希分歧。见 `rc-runtime-rollout.json`、`rc-runtime-duplicate-out/`、`rc-runtime-duplicate-in/`、`rc-state-sync-result.json`。

## 发布流程修复

1. 容器构建读取 Git VCS 信息失败：禁用隐式 VCS stamping，使用 CI 明确传入的 commit 写入程序版本信息。
2. 容器 root 创建产物目录导致 runner 无法写 SHA-256 文件：宿主 runner 在启动容器前创建目录。
3. RC CI 分别使用原生 AMD64 与 ARM64 runner，执行真实目标架构的静态包和 Docker 启动检查。Runner 标签来自 [GitHub 官方文档](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)。

上述没有新增共识状态或存储迁移修改。首次失败 CI 与修复后 CI 均保留，不用远程缓存中的旧成功记录替代当前 commit 的结果。
